- 计划主题：个体冲突全链路与参与者快照门禁
- 工作分支：`v6/participant-contracts`
- 当前基线：`7fe7bfbd118e795e1c309b7e7eccceaf965c0c69`

- 依据：`docs/design/第六版实现内容设计.md` 第 7 至 15 节，以及第六版第一阶段的实际代码和验证结果

## 1. 目标与完成定义

本阶段把第一阶段已经建立的参与者事实、seal 和 request snapshot v3 继续贯通到个体冲突求解、草稿调整和发布门禁。阶段结束时，`enrollments` 模式应成为一条可验证的业务路径，而不是停留在“合同已存在但稳定拒绝”的中间状态。

完成定义如下：

1. `enrollments` 输入携带由当前 seal 快照确定性生成的 `student_overlap_edges`，不再退化为 `groups_only`。
2. scheduler 对每条重叠边建立同一时间段内的硬约束，并输出稳定的 `student_exam_clash` 诊断。
3. `groups_only` 的历史数据、v1/v2 request snapshot 和现有群体互斥语义继续兼容。
4. 同步排考、异步作业、重排和重试都消费同一个冻结参与者快照；重试不得重新读取当前报名表。
5. 草稿从来源运行继承参与者快照，草稿校验、建议、增量重排和发布不回读当前报名事实。
6. 运行、草稿和回滚目标在发布前执行参与者版本、模式和 digest 的 stale 检查；过期目标稳定返回 `409 participant_snapshot_stale`。
7. 真实 PostgreSQL、API、scheduler、shared 和跨语言合同均有可复现的正向、负向和兼容证据。
8. 参与者名单、完整报名集合和完整重叠边不进入普通日志、审计 payload 或非管理员响应。

本阶段完成不等于第六版整体完成。证据包、健康状态展示和个体冲突可视化仍属于后续阶段；本阶段也不触发 Runner、TCR、正式部署或生产数据写入。

## 2. 范围与停止线

### 2.1 本阶段包含

- shared、TypeScript application、Python scheduler 和 OpenAPI 的个体冲突合同；
- 重叠边进入 scheduler 输入并参与 CP-SAT 硬约束；
- `student_exam_clash`、`student_overlap_edge_invalid` 和 `participant_snapshot_stale` 的稳定错误语义；
- 同步、异步、重排、草稿和发布使用统一的参与者快照；
- 草稿快照持久化、迁移兼容和 stale 发布／回滚门禁；
- 内存仓储与真实 PostgreSQL 的同语义回归；
- 固定跨专业选修、重修、名单互斥、快照过期和历史兼容样例。

### 2.2 本阶段不包含

- Excel 导入中台、通用导入质量中心或真实教务系统同步；
- 学生个人账户、个人学生门户和完整学生身份模型；
- overlap-edge 独立事实表；重叠边继续由冻结报名快照确定性派生；
- 个体连续考试等软约束、Pareto 比较、自动策略推荐或多目标优化；
- 复杂关系图、热力图、完整 Web 冲突工作台和新的 Playwright 视觉基线；
- Runner、TCR、服务器、正式域名、生产镜像或数据库部署。

### 2.3 待用户确认的取舍

本计划默认采用以下方案，用户确认前不开始实现：

1. 在 `schedule_drafts` 中增加受保护的 `participant_snapshot` JSONB 元数据，使草稿可以独立追溯来源快照；不新增重叠边表。
2. 第二阶段先完成 API 和算法合同，参与者健康区与冲突解释页面放到第三阶段；必要的 Web 只补最小错误状态，不扩展新工作台。
3. stale 发布和 stale 回滚目标在同一阶段完成；已发布版本不因报名变化被静默撤销，但新的发布目标必须重新 seal 并匹配当前 digest。
4. 旧第五版运行和草稿没有报名快照时，按 `groups_only`／`not_required` 兼容解释，不回填虚构的个体数据。

### 任务 5：stale 运行、发布与回滚门禁

**目标：**

在不可变快照基础上，阻止旧参与者语义成为新的公开发布版本，同时保留已发布版本的历史可追溯性。

**依赖与并行：**

依赖任务 4。必须在事务和并发测试完成后才能进入阶段收尾。

**范围与非范围：**

- 发布运行、发布草稿和选择回滚目标时，在数据库事务中锁定批次并比较当前模式、数据版本、digest 与目标快照。
- 当前批次仍为 enrollment 且未 complete、版本不同或 digest 不同，返回 `409 participant_snapshot_stale`；不进入自动重试。
- 已发布版本不因参与者修改被静默撤销；新发布前必须重新 seal 和重新排考。
- stale 拒绝可以写入脱敏审计摘要，但不得保存完整学生、报名或边集合。
- 发布并发、publication version 和 stale 检查必须在同一事务语义下成立。
- 不改变第五版已有的发布版本 CAS、角色权限和审计失败回滚合同。

**实现边界：**

重点范围为 `apps/api/src/services/draft-service.ts`、`publication-service.ts`、`repository.ts`、`postgres-repository.ts`、shared 错误 DTO 和 API 测试。回滚接口应明确“撤销当前指针”与“选择历史目标”的语义；若现有 API 只执行撤销，则仍须对当前已发布运行的快照状态给出稳定、可解释的处理规则。

**测试策略：**

- seal 后修改报名，旧运行发布失败；
- seal 后修改报名，旧草稿发布失败；
- stale 回滚目标失败且批次发布指针不改变；
- 当前快照匹配时发布和回滚成功；
- 两个并发发布请求中只有一个成功，stale 和 publication conflict 不互相覆盖；
- 内存与真实 PostgreSQL 复现相同状态转换和错误码；
- 验证失败不产生半条运行、半条审计或错误的发布指针。

**验收证据：**

- stale 运行、草稿和回滚目标不能成为新的发布版本；
- 已发布版本仍可查询、审计和解释，不被静默删除；
- API、数据库事务和内存仓储的错误语义一致；
- 不会把业务 stale 错误当作 Worker 可重试的基础设施故障。

**文档同步：**

在 `docs/status/code_review_status.md` 仅记录真实发现的问题；稳定合同和取舍回写 design，完成事实写入 status。

- **前置研究：** 当前设计已经足以启动合同和 scheduler 实现；不再为“是否使用 overlap edge”另建探索性原型。
